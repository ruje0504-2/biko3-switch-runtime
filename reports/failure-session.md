# 失败场景与重试流程

当前应用已接通真实游戏触发失败 → 保留场景的失败镜头/语音/对话 → 重试菜单 → 重新加载原关卡，或返回标题。原流程为2→50→40→50→68→50→2/1。主机普通与ASan/UBSan完成真实输入往返；Switch NVK已交叉构建。完整游戏、Windows整帧视觉对照及Switch实机验证仍未完成。

## 实现

- `game/failure_frame`恢复原51b244的六类结局分派：实际失败相机、角色隐藏/动作及首次到达时的语音或道具音重播；随后严格执行玩家、NPC、背景、道具四个表现阶段。不再执行控制、AI位移、拾取和碰撞。
- 原4eb0ee重新建立玩家姿态与GPU资源，保留NPC、跟随轨道、关卡和照片；恢复玩家初始化中实际改写的动作/交互字段，清除response，保持原未改写状态。NPC语音PT13000..PT53000来自bk3_06，加载时不播放，到达失败镜头时才从头播放。道具分支重播当前实际声音缓冲。
- `scene/failure_session`载入i01_04..i05_04与Type_S.FTT。各结局标签、第二条结局6消息、文字缓存与面板/提示/黑幕严格由已对照的原51afcb控制。NPC等待时间绑定+854，不能误写+840。
- 玩家被重新注册到全局绘制树尾部；NPC/道具/背景及其注册关系保留。相机仍遵循先旧world朝向后新位置的原顺序。失败显示使用模式0x40的玩家透明度与NPC标志。
- `scene/retry`恢复原4eb9d4/51bbe9的六张真实图片、两阶段确认、鼠标即时命中、方向键指针定位、音效、光标计时、共享黑幕和返回路径。只推进当帧实际绘制的按钮精灵。构造保留选择/阶段及共享状态；完成转场后才清零相应字段。
- `app/play_session`拥有失败和重试CPU状态，复用同一common/flow/cursor。逻辑释放先停声音，GPU资源保留到最终快照提交后、下一次帧外回收。重试进入游戏保留previous=0x68并采用原phase2开场，最终自然交接到phase1。

## 验证范围

- 原4eb0ee资源/文本表30配置、原4bf7db玩家重载2400份非零保留状态一致。
- 原51b244分派12000帧、56100次回调、978次重播及6条失败前缀一致。
- 原4eb9d4构造25配置，原51bbe9含自然转场10300帧、57352次绘制、10129次服务事件一致。x87比较的C3位已通过实际指令执行确认：静止指针才保留空闲计时。
- 实际CPU资源组合覆盖5组×6结局、2700帧、90次字形上传、5184000份PCM采样；普通与ASan/UBSan音频hash同为dc31b61e287de260。这部分结局输入是显式组件夹具。
- `failure-flow-probe`只提供正常按钮输入，不改游戏/UI状态。首关开场994帧；上方向行走自然触发失败，等待720帧后确认进入菜单，选择重试，原phase2开场995帧后恢复游戏；再次自然失败并从菜单返回标题。正常运行两次玩法帧为589/726、结局为3/2，菜单转场187/63帧。启动RNG种子来自真实时间，帧数/结局不要求跨进程相同。最终内存版本日志见JSON。
- 查看1280×720 Vulkan回读的失败对话与重试菜单；不宣称与Windows截图逐像素相等。
- 实际应用1700帧标题/开场/两照片/暂停恢复/返回标题回归通过。7项针对性CTest、5项ASan/UBSan单元与Python模块边界通过。
- 最新NRO与验证证据的摘要记录于`failure-session-verification.json`。Mac仍由原caffeinate进程保持唤醒，未修改系统电源设置。
